# Ускорение аннотации видео (`/detect/video/visualize`)

Дата: 2026-09-24. Ветка `feat/video-annotation-speedup`.

## 1. Зачем

Единственный клиент — frigate-analyzer. Кнопка «Annotated» в уведомлении Telegram вырезает запись ±1 мин вокруг события и отправляет её на аннотацию: yolo26x, `imgsz=1024`, `detect_every=1`, фильтр классов. Человек ждёт результат в Telegram, прогресс обновляется опросом раз в 3 с. Через `/export` приходят и более длинные интервалы. Значит, важна задержка одной задачи.

Эталонная задача `09a599cd4b74` на RTX 3090: HEVC 2560×1920, 12.46 кадра/с, 1606 кадров (128 с). Она заняла 76.8 с: проход 1 — 54.5 с (29.5 кадра/с), проход 2 — 22.4 с. GPU был загружен на 70–80 %, процессор — на одно ядро.

Замеры показали две причины:

- **Проход 1 идёт последовательно в одном потоке.** Python читает из пайпа кадр на 14.7 МБ, прогоняет YOLO и только потом читает следующий. Пайп вмещает 64 КБ, поэтому декодер стоит, пока считает GPU, а GPU стоит, пока Python читает и ресайзит кадр. yolo26x работает в FP32 по одному кадру: 25 мс на кадр против 13.5 мс в FP16.
- **В проходе 2 один поток по очереди читает из декодера и пишет в энкодер, копируя каждый кадр два лишних раза.** ffmpeg переводит каждый кадр YUV → BGR и обратно ради нескольких рамок: около 50 с процессорного времени на эталонный ролик. Нижняя граница прохода — NVENC: ffmpeg NVDEC → NVENC без Python проходит ролик за 9.8 с.

Одноразовый прототип на копии результата эталонной задачи (то же разрешение, кодек и длина) сократил время с 86.3 до 33.3 с, в 2.6 раза. Бенчмарк шёл медленнее продакшена, потому что делил GPU с рабочим сервисом. Все замеры собраны в приложении.

## 2. Принятые решения

| Решение | Обоснование |
|---|---|
| Архитектура прежняя: два прохода через процессы ffmpeg, стабилизатор между ними | Вариант A из трёх. Полный GPU-пайплайн (декод в видеопамять, отрисовка на GPU, PyNvVideoCodec или torchcodec) работает только на NVIDIA, тянет тяжёлые зависимости и почти ничего не добавляет: в варианте A проход 1 уже загружает GPU на 93 %, а проход 2 упирается в NVENC |
| TensorRT откладывается | Engine привязан к модели GPU, версии TensorRT и размерам входа, образ растёт на 1.5–3 ГБ. Его можно добавить поверх этого дизайна без переделки |
| Кадр для инференса уменьшает cv2 INTER_LINEAR в потоке-читателе, а не ffmpeg | Масштабирование в ffmpeg меняет детекции: на 400 кадрах слабых детекций стало 287 (bicubic), 204 (bilinear) и 447 (area) вместо 485. cv2 в потоке даёт тот же вход модели, что и `LetterBox` в Ultralytics, бит-в-бит (проверено: расхождение 0) |
| FP16 по умолчанию включён только на NVIDIA | Инференс yolo26x@1024 ускоряется в 1.9 раза. Все карты NVIDIA-образа (torch cu130, `sm_75` и новее) считают FP16 быстро. На AMD FP16 вызывает новые компиляции MIOpen, а это известный триггер утечки дескрипторов, и замера там нет. На CPU FP16 медленный или не работает |
| Батч по умолчанию: 8 на NVIDIA, 1 на AMD и CPU | На yolo26x батч даёт +10 %, на лёгких моделях больше. На AMD новые формы тензоров снова означают новые компиляции MIOpen |
| Обе настройки задаются переменными окружения, одинаковыми во всех образах, по умолчанию `auto` | У пользователей разные карты. Любой сервер переопределяется в `.env` |
| Видео-задачи получают отдельный экземпляр модели | Ultralytics переводит веса общего экземпляра в FP16 на месте и пересоздаёт predictor при каждой смене `quantize`. Параллельный `/detect` на той же модели падал бы на несовпадении типов |
| Проход 2 гонит кадры в YUV420p и рисует рамки прямо на плоскостях | Убирает две конвертации swscale и вдвое сокращает трафик пайпов: 16.1 → 10.0 с. Результат визуально неотличим, пиксели вне рамок совпадают с исходником |
| Цвет рамок в YUV считается по BT.601, limited range | Так текущий энкодер переводит BGR в yuv420p: у результата нет тегов цвета, и swscale берёт BT.601 по умолчанию. Рамки выглядят как раньше |
| При нехватке видеопамяти батч делится пополам | На маленькой карте imgsz 2016 с батчем 8 может не поместиться |
| Энкодер при отмене не убивается | Сохраняется текущая семантика, `api.md`: «жёстко убивать ffmpeg — не цель» |
| Разбивка прогресса 0–80 % на проход 1 и 80–99 % на проход 2 не меняется | Соотношение проходов по времени почти не меняется: около 70/30 и до, и после |

## 3. Поток данных

Два прохода и стабилизатор между ними остаются. Меняется то, как кадры идут через каждый проход.

**Проход 1: сбор детекций**

```
ffmpeg (NVDEC / VAAPI / CPU) → полный кадр BGR24 → пайп 1 МБ
  └→ поток-читатель: чтение в переиспользуемый буфер → cv2 INTER_LINEAR до размера инференса → очередь
       └→ основной поток: набирает батч → model.predict(список кадров, FP16 или FP32)
                          → рамки × (W/w, H/h) → RawDetection
```

Кадры, на которых детекция не нужна (`detect_every > 1`), читатель читает и отбрасывает, чтобы нумерация кадров не сбилась.

**Стабилизатор** не меняется. После прохода 1 сервис освобождает кеш видеопамяти PyTorch (`torch.cuda.empty_cache()`), чтобы NVENC и NVDEC хватило памяти.

**Проход 2: отрисовка**

```
ffmpeg (декод) → YUV420p → пайп
  └→ основной поток: чтение в буфер из пула → рамки на плоскостях Y/U/V → очередь
       └→ поток-писатель: запись без копий → ffmpeg (NVENC / VAAPI / x264 + звук)
```

Не меняются: API и ответ, стабилизатор, политика кодека и битрейта, откат с NVENC на CPU-энкодер, семантика отмены, число кадров в результате.

## 4. Компоненты

### 4.1. `app/ffmpeg_pipe.py`

- **Формат кадра.** `FFmpegDecoder` и `FFmpegEncoder` получают параметр `pix_fmt`: `bgr24` (по умолчанию) или `yuv420p`. Декодер отдаёт `frame_shape` (форма массива кадра) и `frame_size` в байтах. Функция `frame_shape(w, h, pix_fmt)` даёт `(h, w, 3)` для `bgr24` и плоский размер `w*h + 2*ceil(w/2)*ceil(h/2)` для `yuv420p`.
- **`FFmpegDecoder.read_into(buf) -> bool`** читает кадр целиком прямо в переданный буфер и возвращает `False` на чистом EOF. На падении ffmpeg поднимает `RuntimeError`, как сегодня `read_frame()`. Короткие чтения повторяются. `read_frame()` остаётся тонкой обёрткой над `read_into`: для `bgr24` отдаёт массив `(h, w, 3)`, как сегодня, для `yuv420p` — плоский массив `uint8`.
- **`FFmpegDecoder.abort()`** убивает процесс, чтобы вернулось чтение, заблокированное в другом потоке.
- **`FFmpegEncoder.write_frame()`** пишет буфер через `memoryview`, без `tobytes()`. Семантика EOF и падений прежняя.
- **Пайпы** увеличиваются до 1 МБ через `F_SETPIPE_SZ`, если ОС позволяет. Ошибки игнорируются.

### 4.2. `app/frame_threads.py` (новый)

- **`ThreadedFrameReader(decoder, transform, queue_size)`** читает кадры в фоновом потоке в один переиспользуемый буфер формы `decoder.frame_shape` и кладёт в очередь `(frame_num, transform(frame_num, frame))`. Буфер переиспользуется, поэтому `transform` возвращает новый объект или `None`. Основной поток перебирает пары итератором.
- **`ThreadedFrameWriter(encoder, frame_shape, pool_size=4, queue_size=2)`** держит пул буферов формы `frame_shape`. Её даёт декодер прохода 2: основной поток читает кадр прямо в буфер писателя. Методы:
  - `acquire()` берёт буфер из пула;
  - `submit(buf) -> bool` ставит его в очередь записи;
  - `release(buf)` возвращает неиспользованный буфер.

  Фоновый поток пишет через `encoder.write_frame()` и возвращает буферы в пул. `submit` отдаёт `False`, когда энкодер штатно завершился раньше (`-shortest`).
- **Ошибки и остановка.** Исключения фонового потока поднимаются в основном: у читателя при следующем получении кадра, у писателя при следующем `acquire`/`submit` или при закрытии. Оба класса — контекстные менеджеры с протоколом остановки из раздела 6. Потоки помечены daemon.

### 4.3. `app/batch_inference.py` (новый)

- **`inference_size(width, height, imgsz, stride) -> (w, h)`** считает размер кадра под инференс ровно как `LetterBox` в Ultralytics: `imgsz` сначала округляется через `check_imgsz` из Ultralytics, затем `r = min(imgsz/H, imgsz/W)` и `(round(W*r), round(H*r))`. Stride берётся из модели так же, как в Ultralytics: `max(stride, 32)`.
- **`resolve_inference_mode(fp16, batch_size, device) -> InferenceMode(fp16, batch_size)`** превращает значения настроек в режим (раздел 5).
- **`BatchDetector(model, class_names, conf, imgsz, max_det, fp16, batch_size, scale)`** даёт методы:
  - `add(frame_num, frame)` копит кадры и запускает `predict`, когда батч полон;
  - `flush()` досчитывает остаток;
  - `detections: dict[int, list[RawDetection]]` и `detected_frames` возвращают результат.

  `predict` получает список кадров, при включённом FP16 ещё и `quantize=16`. Рамки переводятся в координаты полного кадра множителями `scale = (W/w, H/h)` и дают те же `RawDetection`, что сегодня `_extract_raw_detections`. Нехватку видеопамяти обрабатывает раздел 6.

### 4.4. `app/visualization.py`

- **Общая геометрия подписи.** Расчёт положения подписи (размер текста, прямоугольник фона, точка текста) выносится в помощник, общий для BGR и YUV. Так пути не разойдутся.
- **`draw_detection_yuv420(frame, width, height, det, line_width, show_labels, show_conf, font_scale, text_thickness)`** принимает плоский буфер `uint8` с кадром yuv420p, остальные параметры те же, что у `draw_detection`. Рамку он рисует на плоскости Y толщиной `line_width` и на U/V в половинных координатах толщиной `(line_width + 1) // 2`. Подпись рисуется в BGR на фрагменте, выровненном по чётным координатам. Фрагмент переводится в YUV по BT.601 (limited range, цветность — среднее 2×2) и вклеивается с обрезкой по краям кадра.

### 4.5. `app/video_annotator.py`

- **Конструктор** получает `fp16: bool = False` и `batch_size: int = 1`. Значения по умолчанию повторяют сегодняшнее поведение.
- **Проход 1** работает на `ThreadedFrameReader` с очередью в два батча (`queue_size = 2 × batch_size`) и `BatchDetector`. Проход 2 — на `read_into`, `draw_detection_yuv420` и `ThreadedFrameWriter`.
- **После прохода 1**, если модель на GPU, вызывается `torch.cuda.empty_cache()`.
- **Откат NVENC → CPU** остаётся как есть и тоже идёт через YUV-путь.
- **Логи.** В строку «Starting annotation» добавляются FP16 и размер батча, в итоговую — время и fps каждого прохода. `AnnotationStats` и ответ API не меняются.

### 4.6. `app/model_manager.py`

**`get_video_model(name) -> ModelEntry`** загружает отдельный экземпляр модели из того же файла на то же устройство: для предзагруженной модели — устройство из `YOLO_MODELS`, для остальных — `YOLO_DEVICE`. `name=None` означает модель по умолчанию, как в `get_model`. Параллельные вызовы для одного имени загружают модель один раз, под блокировкой на имя, как в `get_model`. Экземпляры кешируются в своём словаре, выгружаются по `YOLO_MODEL_TTL` простоя общим циклом очистки и освобождаются при остановке. `/models` не меняется.

### 4.7. `app/config.py`, `app/main.py`

- **Настройки.** Две новые строки в `Settings`: `video_fp16` и `video_batch_size`. Валидаторы описаны в разделе 5.
- **Worker** берёт модель через `get_video_model`, определяет устройство по параметрам модели, вызывает `resolve_inference_mode` и передаёт режим в `VideoAnnotator`. Эндпоинт по-прежнему проверяет модель через `get_model` до загрузки файла.

### 4.8. Развёртывание, зависимости, документация

- **Compose.** `VIDEO_FP16` и `VIDEO_BATCH_SIZE` прокидываются во всех шести compose-файлах как `${VAR:-}`. Это стережёт `tests/test_compose.py`.
- **Документация:**
  - `docker/deploy/.env.example` — описание обеих переменных;
  - `CLAUDE.md` — таблица модулей, раздел конфигурации, абзац Video Annotation;
  - `.claude/rules/api.md` — задержка отмены в проходе 1 теперь ограничена одним батчем, а не одним кадром.
- **`requirements.txt`:** `ultralytics>=8.4.150,<9.0.0`. Это первая версия с параметром `quantize`, проверено по дистрибутивам с PyPI: в 8.4.149 его ещё нет. Устаревший `half` пишет предупреждение в лог на каждом вызове.

## 5. Настройки

| Переменная | Значения | `auto` на NVIDIA | `auto` на AMD и CPU |
|---|---|---|---|
| `VIDEO_FP16` | `auto`, `true`, `false` | `true` | `false` |
| `VIDEO_BATCH_SIZE` | `auto`, 1–64 | 8 | 1 |

Как разбираются значения:

- **Регистр** не важен, пустое значение означает `auto`, как у `WATCHDOG_*`. Прочее отклоняется при старте.
- **«NVIDIA»** определяется по устройству модели, а не по `VIDEO_HW_ACCEL`, потому что настройка касается инференса, а не кодека. Условие: устройство `cuda` и `torch.version.hip is None`. В AMD-образе torch тоже называет устройство `cuda`, но это ROCm-сборка, и она относится к AMD.
- **`VIDEO_FP16=true` на CPU** даёт предупреждение в лог и работу в FP32.

Чтобы проверить FP16 и батч на AMD, достаточно задать в `.env` этого сервера `VIDEO_FP16=true` и `VIDEO_BATCH_SIZE=8`.

## 6. Ошибки, отмена, ресурсы

**Ошибки.** Фоновые потоки передают исключения основному потоку без изменения текста:

- падение декодера в проходе 1 роняет задачу с тем же сообщением, что сегодня;
- падение энкодера в проходе 2 доходит до классификатора ошибок NVENC, и тот повторяет проход 2 на CPU-энкодере, как раньше;
- штатный ранний выход энкодера (`-shortest`, код 0) останавливает подачу кадров.

**Остановка без зависаний.** Операции с очередями идут с таймаутом и проверяют флаг остановки. Читатель прохода 1 останавливается в таком порядке:

1. основной поток ставит флаг остановки;
2. `decoder.abort()` убивает процесс-декодер, и заблокированное чтение возвращается;
3. основной поток дожидается фонового потока с таймаутом;
4. контекст декодера закрывает пайпы.

Просто закрыть пайп из основного потока нельзя: `BufferedReader.close()` в CPython ждёт завершения чтения в другом потоке. При ошибке или отмене писатель прохода 2 дописывает текущий кадр, выбрасывает очередь и выходит. Затем контекст энкодера закрывает stdin, и ffmpeg штатно финализирует файл, как сегодня.

Писатель при закрытии ждёт свой поток без таймаута. Сразу после этого энкодер закрывает stdin, и медленный CPU-энкодер, которому на кадр 4K нужны секунды, должен успеть дописать очередь. Зависший энкодер так же блокировал и старый однопоточный цикл.

**Отмена:**
- в проходе 1 флаг проверяется на каждом кадре из очереди, то есть задержка не больше одного батча (около 0.1 с на 3090);
- в проходе 2 — на каждом кадре;
- время до статуса `cancelled` не меняется.

**Видеопамять:**
- **Нехватка памяти** (`torch.cuda.OutOfMemoryError`) на батче больше 1:
  - сервис освобождает кеш;
  - делит батч пополам и считает те же кадры заново;
  - пишет в лог один WARNING с новым размером.

  Повтор идёт вне блока `except`, чтобы трейсбек отпустил тензоры. Уменьшенный батч действует до конца задачи, следующая начинает с настроенного. На батче 1 нехватка памяти остаётся ошибкой задачи.
- **Проход 1** на yolo26x с батчем 8 в FP16 держит до 2.2 ГБ кеша, `empty_cache()` после прохода его отдаёт.
- **Отдельный экземпляр** yolo26x занимает около 110 МБ в FP16 и 220 МБ в FP32 до выгрузки по TTL.

**Оперативная память** ограничена и не зависит от длины видео:
- проход 1 — один полнокадровый буфер и очередь максимум из двух батчей уменьшенных кадров, около 40 МБ;
- проход 2 — пул из четырёх кадров YUV, около 30 МБ при 2560×1920 и около 50 МБ при 4K.

**`/health` и watchdog** не затронуты. Задача идёт в executor, event loop свободен, тяжёлая работа (пайпы, cv2, torch) отпускает GIL.

**`/detect` во время видео-задачи** может ждать, пока GPU досчитает текущий батч: до ~100 мс при батче 8 на yolo26x против ~25 мс сегодня.

## 7. Тестирование и проверка

Тесты гоняются в venv, как описано в `CLAUDE.md`. Записи камер в репозиторий не попадают: он публичный, поэтому интеграционные тесты используют только клипы, сгенерированные `lavfi`.

**Модульные тесты:**

- **`frame_threads`** на фейковых декодере и энкодере:
  - порядок кадров и EOF;
  - ошибки обоих потоков доходят до основного;
  - остановка при заблокированном чтении укладывается в таймаут;
  - при исключении писатель выбрасывает очередь, при чистом выходе дожидается медленного энкодера;
  - буферы возвращаются в пул;
  - ранний EOF энкодера останавливает запись.
- **`batch_inference`** на фейковой модели:
  - неполный последний батч, сопоставление результатов с номерами кадров;
  - пересчёт рамок в полный кадр;
  - `quantize=16` передаётся только при FP16;
  - при нехватке памяти батч делится, и детекции совпадают с прогоном без неё;
  - на батче 1 нехватка памяти пробрасывается.
- **Ресайз против настоящего `LetterBox`** из Ultralytics, без модели. Входные тензоры модели должны совпасть байт-в-байт для кадров:
  - 4:3, 16:9, вертикальных, нечётных размеров;
  - меньше `imgsz` (увеличение);
  - при `imgsz`, не кратном 32.

  Тест поймает момент, когда Ultralytics поменяет свой ресайз.
- **Отрисовка в YUV против BGR** на синтетическом кадре:
  - вне рамок пиксели совпадают бит-в-бит;
  - рамки и подписи совпадают с допуском;
  - отдельно проверяются обрезка подписи у края кадра, нечётные координаты и `line_width=1`.
- **`ffmpeg_pipe`:**
  - `pix_fmt` в командах, размер кадра YUV420p;
  - `read_into` на полном кадре, EOF и падении;
  - `abort()`;
  - запись буфера без `tobytes()`.
- **Настройки:**
  - разбор значений: пустое, `auto`, `true`, `false`, `8`, `0`, `65`, мусор;
  - режим `auto` для CUDA, ROCm и CPU;
  - явные значения поверх `auto`;
  - FP16 на CPU выключается с предупреждением.
- **`get_video_model`:**
  - экземпляр отдельный от `get_model`;
  - кешируется между вызовами;
  - выгружается по TTL и при остановке;
  - модель по умолчанию выбирается как в `get_model`.
- **Обновление существующих тестов:**
  - `test_video_annotator`: мок `predict` отдаёт результат на каждый кадр батча, проход 2 получает YUV-кадры;
  - `test_worker`: используется `get_video_model`;
  - `test_ffmpeg_pipe`: новые параметры;
  - `test_compose`: новые переменные.

**Интеграционный тест** с настоящим ffmpeg, в стиле `test_video_extraction_integration.py`: клипы `lavfi`, CPU-кодеки, фейковая модель с фиксированной рамкой, `annotate()` целиком. После прогона проверяется:
- результат декодируется;
- число кадров совпадает со входом;
- звук на месте;
- на линии рамки стоит её цвет.

Клипы покрывают то, что приходит с реальных камер:
- со звуком и без звука;
- полный диапазон `yuvj420p`;
- звук короче видео (`-shortest` заканчивает запись раньше, писатель должен это пережить);
- переменный fps (проходы 1 и 2 должны насчитать одинаковые кадры).

**Проверка на 3090.** Результаты идут в описание PR:
1. Собрать NVIDIA-образ из ветки и запустить его отдельным контейнером на свободном порту. Рабочий сервис не трогается.
2. Отправить через API ролик с параметрами frigate-analyzer (yolo26x, `imgsz=1024`, `conf=0.6`, `detect_every=1`, те же классы). Подойдёт копия эталонного ролика (результат задачи `09a599cd4b74`) или свежая запись той же камеры. Записи в репозиторий не попадают.
3. Сравнить `processing_time_ms` и время проходов в логе с эталоном: 76.8 с на продакшене.
4. Посмотреть кадр результата глазами.
5. Убедиться, что `/health` отвечает во время задачи.

**Проверка на AMD и CPU.** Её проводит исполнитель на хостах, которые укажет владелец:
- AMD с `auto`: формы тензоров и FP32 прежние, новых компиляций MIOpen нет. Затем эксперимент с `VIDEO_FP16=true` и `VIDEO_BATCH_SIZE=8`. По его итогам можно отдельной задачей поменять `auto` для AMD.
- CPU-образ: полный прогон на реальном ролике.

## 8. Вне рамок

- TensorRT и полный GPU-пайплайн.
- FP16 и батчи для `/detect` и `/detect/video`.
- Параллельная обработка нескольких задач или наложение проходов разных задач.
- Выборка кадров фильтром `select` при `detect_every > 1`. frigate-analyzer шлёт `detect_every=1`, а выборка усложняет нумерацию при CFR-синхронизации ffmpeg.
- Изменения стабилизатора, API и frigate-analyzer.
- Перенос тегов цвета из исходника в результат: результат, как и сейчас, без тегов.

## 9. Риски

| Риск | Что с ним делаем |
|---|---|
| FP16 переключает детекции у самого порога: на эталоне 40 кадров из 400 с уверенностью ≥ 0.6 вместо 34 | Это численный шум. `VIDEO_FP16=false` возвращает FP32 |
| Координаты рамок изредка сдвигаются на 1 пиксель: пересчёт в полный кадр идёт другим путём | Для визуализации несущественно |
| Бит-в-бит совпадение ресайза опирается на внутренности `LetterBox` | Его стережёт модульный тест |
| Протокол остановки потоков сложен | Тесты с блокирующими фейками и таймаутами |
| `/detect` ждёт дольше во время видео-задачи | До ~100 мс. Меньший `VIDEO_BATCH_SIZE` сокращает ожидание |
| Нечётные размеры кадра | Энкодеры отвергают их и сегодня, поведение не меняется |
| 10-битные исходники | ffmpeg переводит их в 8-битный yuv420p, как сегодня переводит в bgr24 |
